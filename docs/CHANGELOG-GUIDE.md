# 变更日志写作指南

> 适用范围：`CHANGELOG.md` 与各文档的「变更日志」表、`docs/release/` 的发布说明。
> 读者是**自己部署/使用的普通用户**，他们读它决定「要不要点更新、更新后去试什么」。
> 一句话：它是产品更新说明，不是变更清单。

## 一、先盘点，再取舍

1. **盘点（不漏）**：`git log --first-parent 上一个版本..HEAD --oneline`，以合并为单位过一遍；拿不准看 diff。
   **以上一个已发版本为基准**：本周期内引入又修掉的问题（新功能刚合入就修的回归），用户从没遇到过，不写。
2. **取舍（好读）**：挑 1～3 件最值得说的当亮点，其余压成一行或一句；重构/CI/测试/文档这类感知不到的不写。
   完整清单交给文末 compare 链接。**「精选叙事 + 完整清单另放」是所有被调研产品的两层结构。**

## 二、结构（无内容的节直接省略）

```markdown
## vX.Y.Z：本版主题（一个短语）

一两句主题段：本版让用户得到了什么，顺手点出其余亮点。

> ⚠️ **需要你动手**：做什么、不做会怎样。
> （不需要时写：✅ 本版无需额外配置，升级后自动生效。）

### 本版亮点

#### 以好处或用户问题为标题

一句痛点 → 现在能做到什么 → 从哪开始用（或「升级后自动生效」）。

### 其他新功能 / 体验改进

- **好处短语**：一句说明，必要时带入口。

### 修好了

- 在哪、做什么时、出了什么问题，现在不会了。
- 以及 N 处细节修复。

### 升级须知

数据库迁移与回退（只在有迁移时写）、已知限制、功能下线。

完整改动见 [vA.B.C → vX.Y.Z](…/compare/vA.B.C...vX.Y.Z)。
```

**第一屏**必须能单独成立：主题标题 + 主题段 + 提示框 + 第一个亮点标题。

## 三、写法规则

1. **一期只推 1～3 个主角**，其余降级成一行。
2. **给版本起名**：「vX.Y.Z：主题短语」。
3. **亮点三拍：痛点 → 现在 → 入口**。入口路径要对照前端代码核实真实菜单名，别凭印象写；只有管理员可见的要注明。
4. **标题讲好处或用户问题，不讲功能名**；例外：主角是用户在界面上看到的名字时，标题里必须出现这个名字。
5. **修复写用户能认出来的症状**：在哪、做什么时、出了什么问题。只单列用户大概率遇到过的，其余并成「以及 N 处细节修复」。
   判断：用户会说「坏了」的（报错、打不开、显示不出、点了没反应）→ 修好了；原本能用只是不够好的（慢、糊、不顺手）→ 体验改进。
6. **要动手的事越危险越靠前，每条都能照做**（命令 / 菜单路径完整）；不需要动手也写一行 ✅——自托管/自部署用户最怕「这次要不要动容器」。
7. **坦白边界**：已知限制、没做完的、要下线的，一句话说清；和某个亮点有关的放该亮点段末，影响全局的放升级须知。
8. **纯修复版不硬凑亮点**：主题直说「这是一个稳定性更新」，列 3～5 条可感知修复即可。
9. **致谢外部贡献者**：以 GitHub PR 作者为准（`git log --format='%an <%ae>'` 只当线索）。
10. **语气**：用「我们 / 你」，平实具体；人格化点到为止。

## 四、不写什么

实现细节（库名版本、协议参数、文件路径、配置项内部名、测量值）· 故障原因分析 · 空话样板（"修复若干问题""优化体验"）· 重复上一版内容。
（HEVC、4K、HDR、MKV 这类用户天天在文件名里见的词可以写。）

## 五、篇幅与自检

- 50 行以内；亮点外每条不超过一行（约 40 汉字）。
- 第一行自检：只看第一屏，知道要不要更新、要不要动手吗？
- 念给不写代码的朋友听：哪句需要解释？每个亮点他知不知道去哪儿试？

## 六、变更日志表（文档内嵌用）

| 版本 | 日期 | 变更 | 负责人 |
|---|---|---|---|

规则：历史行**只增不改**；版本号三处一致（`VERSION` / `CHANGELOG.md` 最新条目 / 任务卡引用）；
主版本=战略架构变化，次版本=章节/流程新增，修订号=文字链接格式。
