> **0.3.3 → 0.3.4**。本轮几乎全部是**修复**，且集中在同一类问题上：

### 🔴 本轮主题：五个"静默失效"的真 bug

这类缺陷**没有任何报错** —— 唯一的症状是"功能没反应"，
比崩溃难查得多。逐条记录根因，便于后人避坑。

| # | 现象 | 根因 | 为什么难发现 |
|---|---|---|---|
| 1 | **Trakt 实时追踪完全不工作** | `seedReverseMap` **方向反转了两次**（调用方传 `seriesId→tmdb`，函数内又反转一次）⇒ 抵消 ⇒ 查不到 | 日志显示"已预热 **5713 条**"——**条数完全正常**，方向却是反的 |
| 2 | **「继续观看」永远推不出去** | `models.dart` 读 `UserData['PositionTicks']`，而 Emby 官方字段名是 **`PlaybackPositionTicks`** ⇒ 恒为 null ⇒ 进度恒 0 | 读不存在的 Map 键**不报错**，只返回 null |
| 3 | 同上（第二个原因）| `detail_page` 塞了个 `-1.0` 占位符当"有位置无百分比"的标记，**但下游从没处理它** | 注释说"交给上层估"，上层却没做 |
| 4 | 转码播放**必然报错** | `transcodingUrl` 缺 `PlaySessionId` | 播放列表本身 200，**只有分段**才 400 |
| 5 | 同上（真根因）| **服务器不具备转码能力**（Emby 免费版无 Premiere） | 分段端点有 `[Required]` 参数，服务端没生成 ⇒ 400 |

> ⚠️ **第 1 条的教训值得单独记**：我一度根据"日志在某行之后空白"
> 断定"代码卡住了"—— **结论是错的**。真相是 **`debugPrint` 在 release 下会
> 节流丢日志**。"日志里没有"**不能**推断为"代码没执行"。

### 📺 Trakt 同步：修好整条链路

| 环节 | 修复前 | 修复后 |
|---|---|---|
| 实时追踪（看一半就上报）| ❌ 静默跳过 | ✅ `[TraktTrack] 上报器就绪` + `start/stop ok p=65.7%` |
| **「继续观看」**（1–79%）| ❌ 从不推送 | ✅ `POST /scrobble/pause` 返回 **201** |
| 「已看」同步 | ✅ | ✅ |
| Emby 进度落库 | 🔴 字段名读错 | ✅ `[EmbyReport] UserData OK` |

**目标集选取规则修正**（跨季时会推错集）：
```
旧：只看季号 ⇒ S2E1(2%) 会盖过 S1E5(40%) ⇒ Trakt 指向第 2 季
新：先按进度降序（看得最多的优先），再比季/集号
```

**HTTP 超时统一**：审计发现 **12 处请求没有任何超时** ——
`Dio()` 的超时默认是 `null`（**无限等待**），网络不通时会永久转圈。
⇒ 三层保险：构造 `BaseOptions` + **拦截器兜底**（覆盖以后新增的请求）+ 逐请求显式。

### 🗂️ 分类浏览：新增「类型」与「排序」

| 行 | 内容 |
|---|---|
| 类别 | 剧集 / 电影 / 动漫 / 综艺 / 纪录片 / 儿童 |
| 地区 | 全部 / 国产 / 港台 / 日韩 / 欧美 |
| **类型**（新）| 按类别给**正确的那套** id |
| **排序**（新）| 默认 / 最热 / 最新 / 最高分 / 最多人看 |

> ⚠️ **TMDB 的 movie / tv 是两套独立 genre id**：
> 电影「动作」= `28`，剧集「动作冒险」= **`10759`**。
> 发错会**筛出 0 条**（不报错）。多值用 `|`（OR）而非逗号（AND）。
>
> ⚠️ `最新` 对电影/剧集用**不同字段**（`primary_release_date` vs `first_air_date`）。

### ⚠️ 已知限制

- **转码不可用**：当前服务器（Emby 免费版）**不具备转码能力** ⇒ 只能直连播放。
  切「转码」会**明确提示**而不是内核报错（本轮修复）
- **无 401 自愈**：token 失效需重新登录（缺陷 7.7，仍在）
- **115 非公开接口**：有账号风控风险，未联调真实播放
- **弹幕发送未做**：只能看，不能发
- **起播偏慢**：网络源约 7–9 秒（受限于网络源探测）
- **安装时会出现「未知来源」警告**：非商店渠道的正常现象，请放心安装
