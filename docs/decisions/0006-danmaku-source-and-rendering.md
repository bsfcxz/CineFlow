## 背景

阶段五（弹幕）此前为 0%。用户给出明确约束：

1. 参考 `misaka_danmu_server`、`danmu_api` 两个项目
2. 弹幕协议以 **`doc.dandanplay.com/open/` 官方文档** 为准
3. **不自建** —— 直连官方，不要自己搭服务
4. 弹弹Play 兼容服务用标准 `/api/v2/comment/{episodeId}`；
   御坂服务（2.7.0+）的异步接口按 `?async=1` + **1.5 秒轮询** + **总上限 5 分钟**
5. 可参考 `CeRu-007/Cmby` 的实现逻辑

需要决策两件事：**从哪取弹幕**（源与认证）、**怎么画弹幕**（渲染引擎）。

---

## 决策一：源策略 —— 双形态并存，默认关闭

| 形态 | 地址 | 认证 | 备注 |
|---|---|---|---|
| **官方（默认推荐）** | `https://api.dandanplay.net` | 请求头签名 | 用户自行申请 AppId/AppSecret |
| **自建兼容服务** | 用户填 | **URL path token** | 兼容 danmu_api 与 misaka_danmu_server |
| **关闭** | — | — | **默认值** |

### 为什么不只支持官方

用户说"不自建"，但**官方 API 在本项目开发网络下不可达**（实测 `api.dandanplay.net`
HTTPS 返回 000，同域 `doc.`/`dev.` 却正常）。同时用户本人提供了两个自建项目的链接。
因此保留自建形态作为**可选配置**，但：

- 默认值是 `off`（不擅自联网、不擅自连第三方服务）
- 两种形态的**认证方式在代码里显式分支**，不做"统一抽象"——
  它们的契约差异是本质的（见下），强行统一必有一边 403

### 为什么两种认证不能统一

- 官方：`X-AppId` / `X-Timestamp` / `X-Signature` 三个头，
  签名 = `base64(sha256(AppId + Timestamp + Path + AppSecret))`
- 自建：token 编在 **URL 路径**里（`/{TOKEN}/api/v2/...`），**完全不看认证头**

调研确认 danmu_api 与 misaka 都不校验签名。若为"代码好看"而统一成"总是发签名头"，
自建服务会因缺少 token 路径而 401/403；反之官方必 403。

### 凭据处理（安全红线）

官方文档第 7 节明确要求**开源客户端不得硬编码 AppSecret**。本项目执行得更彻底：

- 仓库里**连占位符都不放**，由用户在设置页填写
- 存 `flutter_secure_storage`（Android Keystore），与 Emby 凭据同一套保护
- 示例地址用 **RFC 5737 文档网段** `192.0.2.x`（永不路由到真实主机）——
  不用 `192.168.x.x`，否则会命中 `check-secrets.ps1` 的内网地址规则
  （实测踩过，见提交 `38d72f2`）

### 异步生成

按用户规格实现：`?async=1` → 若返回 `status=pending` + `taskId`，
则 **1.5 秒**间隔轮询，**总上限 5 分钟**，完成后**再取一次**普通接口。

三个与直觉不同、调研确认的点（已写进 `danmaku_async.dart` 注释）：

1. `?async=1` **不会立即返回**——服务端仍同步等最多 30s，只在超时才给 pending
2. 状态字面量是 `pending` / `completed` / `failed`，**没有 `done`**
   （按 `done` 判断会一直等到超时）
3. **成功时可能根本没有 taskId**（30s 内完成就直接返回弹幕）→ 必须容忍"同步成功"分支

## 决策二：渲染 —— 自绘 `CustomPainter`，不引入第三方弹幕库

### 候选

| 方案 | 结论 |
|---|---|
| `canvas_danmaku`（MIT） | **不引入**，但**借鉴其算法** |
| `flame_barrage` | 不引入（需引入 flame 引擎，为一个覆盖层太重） |
| 生成 ASS 字幕交给 libmpv | 不采用（控制力差，样式/交互受限） |
| **自绘 `CustomPainter`** | ✅ **采用** |

### 为什么借鉴而不依赖

`canvas_danmaku` 是 MIT，可直接依赖。但我们的需求更窄（只要滚动/顶部/底部三种模式、
无发送交互），而它的 API 模型是"**播放器 push 弹幕进引擎**"：

> 该库没有 seek 概念，只有 add/updateOption/pause/resume/clear
> ——拖动进度条必须 `clear()` + 重新 push 全部弹幕。

而我们的播放器状态是**以时间为唯一事实源**（`_pos` 每帧可用），
自绘层可以直接由 `(弹幕列表, 当前时间)` **纯函数式**算出可见集，
拖动进度条天然正确、无需 clear/重灌。这比适配 push 模型更简单也更不容易出竞态。

**因此采用自绘，但把它最有价值的两条算法抄过来**（并在代码注释里注明出处）：

1. **追尾判据**（`danmaku_layout.dart`）：
   速度模型是 `(屏宽 + 文本宽) / 时长` ⇒ **宽弹幕比窄弹幕快**，会追尾。
   只判"前一条是否已离开"过于保守（密集时大量丢弃）；
   只判"当前是否重叠"又会让宽弹幕真的压过窄弹幕。
   正确判据两条：① 前一条已完全进屏；② 新弹幕追上它的时刻晚于它离开的时刻。
2. **给字幕留一行**（`reserveSubtitleLane`，对应其 `safeArea`）：
   遮挡字幕比"少显示一行弹幕"更影响观感。

### 其他渲染决策

- **弹幕层不吃手势**：`IgnorePointer` 包裹，渲染顺序为
  `视频 → 弹幕 → 控制层`（在视频之上才可见，在控制层之下才不挡按钮）
- **轨道规划缓存在 `State`**：每帧重算会让同一条弹幕落到不同轨道（视觉"上下横跳"），
  且数千条每帧规划会掉帧
- **密集时默认丢弃、可选重叠**（`DanmakuOverflow`）：
  丢弃比乱叠耐看，但把选择权留给用户（对应其 `massiveMode`）
- **失败绝不影响播放**：没配源、网络不通、该片无弹幕、服务端 5xx 都只提示，
  视频照常播（AGENTS.md §5.5 的降级约定）

## 后果

### 正面

- 弹幕协议有 **161 例单元测试**覆盖（签名/匹配/布局/客户端/异步/配置/持久化），
  含**用 Python hashlib 独立算签名交叉验证**（不是自己证自己）
- 修掉一个真实缺陷：原先按 B站 8 段解析官方 `p` 字段，
  会把**字号当颜色**——弹幕颜色全错但不报错
- 测试还抓出**持久化缺陷**：一个字段类型不符会导致**所有**设置退回默认值
  （用户的字号/屏蔽词被连累丢失）——这正是 Cmby 版本历史里反复出现的那类 bug
- 自绘层与播放器时间轴天然同步，无需处理 push 模型的 seek 竞态

### 负面 / 未完成

- **官方 API 未真实联调**：本机网络不可达，协议契约靠单测与 Mock Dio 保证。
  **不得声称"已验证"**
- 自建服务同样未联调（需用户部署）
- 未做：弹幕发送（022）、手动匹配面板（023）、密度折线图（024）、
  大池解析移入 isolate（025）
- 未做 CSS/ASS 样式自定义（仅字号/透明度/显示区域/屏蔽词）

## 备选方案与为何未选

| 方案 | 为何未选 |
|---|---|
| 只支持官方 | 官方在本机不可达，且用户提供了自建项目；但保留为默认推荐项 |
| 只支持自建 | 违背用户"不自建"的指令 |
| 统一两种认证为一种 | 契约本质不同，必有一边失败 |
| 直接依赖 `canvas_danmaku` | 其 push 模型与我们的时间轴事实源不合，适配成本高于自绘；且只要算法不要框架 |
| 生成 ASS 交 libmpv 渲染 | 样式与交互控制力差；libmpv 的 ASS 覆盖层还涉及 OSD 层级问题 |
| 用 flutter 的 Widget 列表渲染弹幕 | 数千条 Widget 的构建/布局开销远高于单 Canvas 绘制 |
