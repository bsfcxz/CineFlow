## 一、目的地（Destination）

> wayfinder 的第一个动作是命名"终点"。**终点决定范围**，所有任务都朝它收敛。

**到达终点 = 一个可以正式分发的 v1.0：**

1. **能装**：release 签名（非 debug），可覆盖安装，任意 arm64 手机可装；
2. **能播**：播放器整页 UI 经**人眼真机走查**（画面出图 / 手势 / 弹幕叠加），
   且有后台播放与通知栏控制；
3. **能发布**：GitHub Releases 上有带校验和的正式产物，README 与事实一致；
4. **能维护**：核心改动有单测与门禁守着，新人（或新 AI 会话）读三份文档即可接手。

**当前距离终点**：约 **70%**。缺口集中在"可分发"与"已视觉验证"两件事上，
而不是功能数量——功能面其实已经比"能发布"所需的更多（115、弹幕都是超前完成的）。

## 七、按 to-spec 模板：下一个要做的功能

> 用 `mp-to-spec` 的模板，把**排序第 2 的「播放器整页走查」**写成规格。
> 它是 4.2 多项的前置，所以值得写清楚。

### 7.1 Problem Statement（用户视角的问题）

内核迁移完成后，**没有任何人真正看过播放器页面的实际表现**。
集成测试只验证了「Dart → MethodChannel → Kotlin → JNI → libmpv」这条链路能起播，
但**用户看到的是播放器整页**：控制层能不能正常显隐、手势滑动会不会误触发、
弹幕层有没有盖住字幕、退出后应用会不会崩。这些都是**只有人眼能判断**的。

风险在于：内核测试全绿会给人"播放已经好了"的错觉，
而实际上**UI 层可能整个是坏的**（比如视频层尺寸为 0、控制层遮挡全屏）。

### 7.2 Solution（用户视角的解法）

在真机上完整走一遍播放流程，**用截图与日志留证**，
把发现的问题立卡，而不是"看起来还行"就过。

### 7.3 User Stories

1. 作为用户，我想点进任意影片就能看到画面，以便确认播放是通的
2. 作为用户，我想轻点屏幕能唤出/隐藏控制层，以便不被打扰地看片
3. 作为用户，我想看到进度条能拖动且立即响应，以便跳到想看的片段
4. 作为用户，我想横向滑动调亮度、纵向滑动调音量，以便躺着也能操作
5. 作为用户，我想看到弹幕浮在画面上且不吃掉我的手势，以便边看边发弹幕
6. 作为用户，我想看到字幕不被弹幕完全遮挡，以便看清对话
7. 作为用户，我想切音轨/字幕/倍速后立即生效，以便适配不同片源
8. 作为用户，我想退出播放后应用不崩溃，以便继续浏览
9. 作为用户，我想退出播放后服务器会话清零，以便下次从头播
10. 作为用户，我想旋转屏幕时布局正确适配，以便横竖屏都可用

### 7.4 Implementation Decisions

- **不改代码，先走查**：这一轮的产出是**一份问题清单 + 截图证据**，不是补丁；
- **走查路径**（按 AGENTS §8.2）：登录 → 首页 → 详情 → 播放 → 返回 → `pidof` 存活；
- **留证要求**：每个 User Story 至少一张截图或一行 logcat；
- **坐标陷阱**：横屏 `input tap` 走竖屏坐标系（`lx = W - py, ly = px`），
  且横屏下 uiautomator 语义大量失效（实测 31 节点仅 9 个有有效 bounds）→
  **横屏优先用 `debugDumpApp` 确认控件存在，点击回竖屏做**；
- **崩溃判据**：必须用 `adb shell pidof com.cineflow.app`，
  **不能凭 `Lost connection to device` 下结论**（那只表示调试连接断了）。

### 7.5 Testing Decisions

- **这一轮不写新单测**（走查本身不是可自动化的行为）；
- 但若发现缺口，**把可逻辑化的部分提为 `public static` 补测试**
  （先例：`PlayerPage.parseDefaultRate`、`LibraryPage.sortDirectionFor`）；
- **回归线**：走查后必须重跑 `integration_test/player_kernel_test.dart`，
  确认没有回归（它守的是内核链路，是唯一能碰到 JNI 的测试）。

### 7.6 Out of Scope

- 不重构播放器 UI（除非发现致命缺陷导致不可用）；
- 不做 K3 会话层（那是下一步）；
- 不测多平台。

### 7.7 Further Notes

⚠️ **走查前必须先重建 APK**：`flutter test integration_test/...` 会污染
`app-debug.apk` 的入口（Dart VM 正常起来但白屏，logcat 无 `[GoCore]`/`[DB]`）。
`check-dev.ps1` 有自动检出（已反向注入验证）。

## 八、执行顺序建议

> 依据：**风险优先 + 前置依赖**。不是按"功能多少"排。

```
第 1 步  提交 42 项改动              ← 先有回滚点，再动别的
          ↓
第 2 步  真机走查播放器整页           ← 是 K3 与列表页重构的前置
          ↓
第 3 步  ┌ 修 README 地址/描述       ← 三项无依赖，可并行
         ├ release 签名（发布前必做）
         └ WakeLock（体验硬伤）
          ↓
第 4 步  401 自愈                     ← 独立，可与 3 并行
          ↓
第 5 步  K3 Media3 会话层             ← 依赖第 2 步的结论
          ↓
第 6 步  列表页 UI 重构                ← 依赖信息架构决策（雾区）
          ↓
第 7 步  审批并发布 v0.3.0             ← 需用户明确批准（分发铁律 D1）
```
